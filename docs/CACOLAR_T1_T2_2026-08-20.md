## T1 — measured response surface

| Point | FUNSD | SROIE | CORD | n | bytes (rel) |
|---|---|---|---|---|---|
| d5/r64 (3 seeds) | 60.41 | 38.75 | 96.34 | 3 | 1× |
| d50/r64 (s42) | 82.29 | 62.42 | 97.12 | 1 | 10× |

Isolated effects (seed 42 unless noted):

- **Coverage** (d5→d50 @ r64): FUNSD **+37.97**, SROIE +21.08, CORD +0.41.
- **Fidelity** (r64→r128 @ d50): FUNSD +2.98, SROIE **+14.49**, CORD −0.15.
- **Selection** (random→kcenter @ d50/r128, 3-seed mean): FUNSD −0.79, SROIE −0.76, CORD +0.44.

### Findings

1. **The dials are separable and task-heterogeneous.** FUNSD (diverse forms) is
   coverage-hungry and rank-insensitive; SROIE (dense receipts) is strongly rank-sensitive;
   CORD needs nothing (≥96.2 at every point).
2. **Selection is a dead dial** at this operating range (confirms the kcenter null) → R3 is
   deprioritized; CA-CoLaR v1 is a 2-dial allocator.
3. **Structural free lunch:** the final task's bank is written but never replayed within the
   stream; uniform CoLaR still pays for it. An allocator may legally spend those bytes.
4. Caveat: the d50/r64 point is single-seed and log-recovered; T4's uniform control fills the
   interior (d10/r64) with a fresh, fully-instrumented run.

## T2 — allocation rule (v1, no learned components)

At bank time for task t, with unit cost docs×rank: spend the stream budget as
**coverage-first for high-diversity tasks, fidelity-first for high-density tasks, zero for
final-task banks**. For the dil stream this instantiates as: FUNSD gets docs, SROIE gets rank,
CORD gets nothing.

## T4 preregistration (recorded BEFORE launch)

- **Budget:** 1,920 doc·rank units ≈ 2× the d5/r64 bank (interior of the scarce regime).
- **Control:** `colar` d10/r64 uniform (3 banks × 10 × 64 = 1,920), seed 42, dil, k4/e5.
- **Treatment:** `colar_adaptive` schedules docs=[20,5,0], rank=[64,128,64]
  (20×64 + 5×128 + 0 = 1,920), same everything else.
- **Guards (vs the equal-byte uniform control):** AA ≥ +0.5; old-domain (FUNSD+SROIE)/2 mean
  ≥ +1.0; no domain < −0.5; wall-time within +10%. Secondary (reported, non-gating):
  old-domain micro-precision deltas.
- **Prediction (falsifiable):** treatment FUNSD ≥ control + 3 (coverage effect at 2×docs) and
  treatment SROIE ≥ control (r128 fidelity offsets d5 coverage); CORD unchanged (≥96).
- Failure → the allocator dies at v1; no schedule sweep. Seeds 7/123 run only on a pass.

## T4 result (2026-08-21) and the one admitted amendment

**Result: PARTIAL PASS.** 79.0358 AA / [81.1966, 59.6685, 96.2423] vs equal-byte uniform
d10/r64 control 71.9307 / [70.2294, 48.3149, 97.2477]. Passes AA (+7.1052), old-domain mean
(+11.1604), runtime (−0.26%), old micro-precision (+10.90/+15.62); **fails the per-domain guard
on CORD (−1.0054 < −0.5)**. All three predictions HIT. Banks 6.29 vs 6.41 MB (parity holds).

### Amendment A1 — re-gate at docs=[18,5,2] (preregistered 2026-08-21, BEFORE running)

Rationale: the per-domain guard was written for augmentation gates (add capacity, harm nothing)
and is mis-specified for zero-sum allocation, where CORD's loss is the funding source. Rather
than relax the guard post hoc, test whether a token CORD bank removes the failure.

- **Treatment A1:** `colar_adaptive` docs=[18,5,2], rank=[64,128,64] — 1,920 units, modeled
  4.915 MB, byte-identical to the T4 treatment (2 CORD docs funded by 2 FUNSD docs).
- **Control:** the SAME uniform d10/r64 run already completed
  (`results/dil_colar_seed42_k4_d10/`) — not re-run; the arms are seed- and budget-matched.
- **Guards:** unchanged from T4 (AA ≥ +0.5, old-domain mean ≥ +1.0, every domain ≥ −0.5,
  runtime ≤ +10%).
- **Prediction:** CORD ≥ control − 0.5 (guard recovered) AND old-domain mean ≥ +8.0 (i.e. the
  2-doc CORD bank costs less than 3.2 of the 11.16 old-domain points).
- **Decision rule:** all guards pass → CA-CoLaR v1 GO, proceed to T5 (seeds 7/123, dil orders,
  cil_cord). CORD recovers but old-domain mean < +8.0 → report as a Pareto trade, still GO but
  the headline becomes the frontier, not a single point. CORD still fails → the per-domain guard
  is genuinely incompatible with allocation; escalate to the user for a guard redesign rather
  than iterating schedules. **No third schedule without an explicit decision.**
