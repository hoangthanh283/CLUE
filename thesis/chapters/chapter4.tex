\section{Framework Selection}
\label{sec:impl-framework}

\subsection{Backbone Selection}
\label{sec:impl-backbone}

The primary backbone is LayoutLMv3-base
(\texttt{microsoft/layoutlmv3-base}, $\approx$\,133M parameters, 12 layers, hidden
size 768). It was chosen because it is document-specific, encoder-only, and small
enough to run the full experimental grid---ten baselines and the selected method
across three scenarios and three seeds---within the compute budget, while exposing
the four separable components central to the diagnosis. LiLT-base and BROS-base
serve as secondary backbones for a generalisation study on a reduced method
subset. Table~\ref{tab:backbone-comparison} compares the candidates. This choice

\subsection{Software Stack: Selection Criteria and Justification}
\label{sec:impl-stack}

\paragraph{Selection criteria.} Five requirements drove the choice of software
stack. \textbf{(i) Reference implementations:} the diagnosis must run on the
canonical LayoutLMv3 weights and preprocessing, not a re-implementation whose
deviations could masquerade as forgetting signal. \textbf{(ii) Composable
configuration at grid scale:} the full grid of methods $\times$ scenarios
$\times$ seeds must be launchable from a single entry point with no per-run code
edits. \textbf{(iii) BIO-correct evaluation:} the metric must be entity-level,
span-aware F1 rather than token accuracy. \textbf{(iv) Queryable experiment
tracking:} the complete grid must be reconstructable from logged runs alone.
\textbf{(v) Determinism support:} the CKA and Fisher patterns reported in
Chapter~\ref{ch:results} must reflect signal, not run-to-run noise, so the
framework must expose deterministic execution modes.

\paragraph{Justification.} PyTorch ($\ge$2.3) satisfies (i) and (v): it is the
framework in which the canonical LayoutLMv3 is released, it provides the
forward-hook API on which the CKA activation probes are built, and it exposes
the cuDNN determinism flags required for reproducible kernels. TensorFlow and
JAX were rejected because neither has a maintained LayoutLMv3 reference
implementation. HuggingFace Transformers ($\ge$4.41) supplies the canonical
LayoutLMv3 model together with its \texttt{LayoutLMv3Processor}, and Datasets
($\ge$4.0) loads the benchmark corpora from the HuggingFace Hub, jointly
covering (i); re-implementing the backbone or hand-rolling loaders would
forfeit the canonical-weights guarantee. PEFT ($\ge$0.11) provides audited LoRA
injection for the LoRA-family baselines, avoiding hand-rolled adapter code.
For (ii), Hydra ($\ge$1.3.2) with OmegaConf composes declarative configuration
groups (method, scenario, model, training) into a fully specified run;
\texttt{argparse} plus hand-rolled YAML was rejected because it cannot express
the sweep grid declaratively. For (iv), Weights \& Biases ($\ge$0.17) records
every run with structured, queryable tags; TensorBoard was rejected because it
offers no structured cross-run querying. Finally, for (iii), \texttt{seqeval}
($\ge$1.2.2) computes entity-level BIO-aware F1; plain token accuracy was
rejected because it is inflated by the dominant O class and would mask
entity-level forgetting. Experiments are launched through a single entry point
and configured by composition, e.g.
\begin{quote}\small
\texttt{python scripts/train.py method=ewc scenario=cil\_cord seed=42
method.lambda\_=1000}
\end{quote}
so that every run is fully specified by its config and reproducible.

\subsection{Why a Bespoke Continual-Learning Harness}
\label{sec:impl-why-bespoke}

The stack above leaves one decision open: whether to build the continual loop on
an established CL framework---Avalanche~\citep{lomonaco2021avalanche},
Mammoth~\citep{boschini2022mammoth}, or PyCIL~\citep{zhou2023pycil}---or to write a
bespoke harness. A bespoke harness was chosen, for three reasons rooted in the
task rather than in preference.

\paragraph{Task-shape mismatch.} All three frameworks are engineered for
image classification: a sample is a single tensor with one integer label, and the
metric is top-1 accuracy. Their training abstractions encode this directly---an
Avalanche \texttt{SupervisedTemplate} reads its input as \texttt{mbatch[0]} and
scores a sample-level criterion; a Mammoth model implements
\texttt{observe(inputs, labels, \ldots)} over a single input tensor with
integer-target task masking; PyCIL slices an image dataset by integer class sets
and herds exemplars on pooled image features. The unit of work here is instead a
tri-modal document---WordPiece ids, normalised boxes, and a page image---carrying
a \emph{per-token} BIO label sequence and scored with entity-level
\texttt{seqeval} F1, a metric absent from all three. Adopting any of them would
require replacing their data, model, loss, and evaluation layers at once, which
amounts to reproducing the loop described in this chapter inside a contract built
for a different task.

\paragraph{Class-incremental at the token level.} The head here is a single linear
layer that \emph{grows} across sessions over a token label space, preserving
trained rows and initialising new ones from $\mathcal{N}(0,0.02)$. The frameworks
either assume a fixed output dimension or grow a head while still routing one input
tensor and one label per sample; class-incremental \emph{token} labelling is not a
supported mode.

\paragraph{Method coverage.} The harness already implements the classical
baselines and the 2024--2025 line---flatness-aware replay, LoRA-based and
prompt-based methods---used in Chapter~\ref{ch:results}. The newest strategy
shipped by Avalanche or Mammoth predates several of these, so adopting a framework
would subtract, not add, capability. These libraries remain the reference for the
classical baselines, whose published algorithm definitions the implementations
follow; control is simply not inverted to them, for the reasons above.

\section{Document-IE Pipeline Integration}
\label{sec:impl-pipeline}

Every document passes through the same five-step preprocessing pipeline,
regardless of dataset or continual scenario:

\begin{enumerate}
  \item \textbf{Load.} Dataset-provided OCR tokens, word boxes, and the page
  image are loaded---no OCR engine is ever run.
  \item \textbf{Tokenise.} The \texttt{LayoutLMv3Processor}
  (\texttt{apply\_ocr=False}) WordPiece-tokenises the words, truncating and
  padding to a maximum sequence length of 512.
  \item \textbf{Normalise layout.} Word boxes are scaled to the integer range
  $[0,1000]^4$ and degenerate or out-of-range boxes are clamped.
  \item \textbf{Encode image.} The page image is resized to $224\times224$ and
  consumed by the backbone as $16\times16$ patches.
  \item \textbf{Align labels.} Each sub-token inherits its word's box, only the
  first sub-token carries the BIO label, and trailing sub-tokens are set to the
  ignore index $-100$.
\end{enumerate}

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=\textwidth,height=0.5\textheight,keepaspectratio]{doc_pipeline}
  \caption{The five-step document preprocessing pipeline. Dataset-provided OCR
  tokens, word boxes, and the page image are tokenised, normalised, and aligned
  into the tri-modal inputs of the backbone; colour chips mark which input
  stream each step feeds.}
  \label{fig:doc-pipeline}
\end{figure}

Figure~\ref{fig:doc-pipeline} summarises the pipeline. The same preprocessing is
shared across all datasets so that the only thing that changes between continual
tasks is the data and label space, not the pipeline. For the diagnostic conditions
(C1--C4) a modality mask is applied at the input layer---zeroing image pixels,
replacing text with padding tokens, or zeroing layout positions---through the
backbone wrapper's \texttt{modality\_mask} forward argument rather than a separate
ablated model, so the four conditions differ only in which input pathways are
active.

\paragraph{Data integrity and validation.} Three preprocessing invariants are
enforced and checked so that the forgetting signal is not confounded by data
artefacts. First, WordPiece token--box alignment is validated at load time: every
sub-token is tied to exactly one word box, the first sub-token of a word carries
that word's BIO label, and the trailing sub-tokens are set to the $-100$ ignore
index so that the loss and the entity-F1 metric see one prediction per word.
Second, bounding boxes are normalised to the $[0,1000]^4$ integer range expected by
the backbone's 2D position embeddings, with clamping to guard against
out-of-range or degenerate (zero-area) boxes. Third, and most importantly for a
controlled diagnosis, the pipeline consumes the dataset-provided OCR transcriptions
and boxes directly and never re-runs an OCR engine; this removes OCR quality as a
confounder, so that any measured drift is attributable to continual training of the
encoder rather than to changing recognition behaviour across tasks.

Chapter~\ref{ch:experimental-setup} specifies the datasets this pipeline
consumes.

Figure~\ref{fig:system-architecture} gives the overall picture: a thin

\subsection{Continual-Learning Core}
\label{sec:impl-cl-core}

All methods implement a common \texttt{ContinualMethod} interface with four hooks:
\texttt{before\_task} (e.g.\ expand the classifier head or allocate a LoRA bank),
\texttt{train\_task} (the training loop), \texttt{after\_task} (update the replay
buffer, compute Fisher, freeze weights), and \texttt{evaluate} (evaluate on all
tasks seen so far). This interface lets regularisation, replay, prompt-based, and
LoRA-based methods share the same training and evaluation harness, which is
essential for like-for-like comparison. Algorithm~\ref{alg:cl-loop} shows how the
core drives these hooks per task.

\begin{algorithm}[t]
  \caption{The continual-learning core loop}
  \label{alg:cl-loop}
  \begin{algorithmic}[1]
    \Require task sequence $\mathcal{T}_{1:T}$, method $m$, backbone $\theta^{(0)}$
    \For{$t = 1$ \textbf{to} $T$}
      \State $m.\texttt{before\_task}(\mathcal{T}_t)$
        \Comment{expand head (Eq.~\ref{eq:head-expansion}); allocate prompts, adapters, penalties}
      \State $m.\texttt{train\_task}(\mathcal{T}_t)$
        \Comment{AdamW, constant LR, val-F1 early stopping; replay/distillation internal to $m$}
      \State $m.\texttt{after\_task}(\mathcal{T}_t)$
        \Comment{update buffers, estimate Fisher, freeze parameters as $m$ requires}
      \ForAll{$j \le t$}
        \State $R[t,j] \gets \textsc{EntityF1}(m.\texttt{evaluate}, \mathcal{T}_j)$
      \EndFor
      \State \textsc{Snapshot}(per-layer CKA, per-group Fisher)
        \Comment{decoupled instrumentation hooks}
    \EndFor
    \State \Return $R$ and derived AA/BWT/AF/FWT
  \end{algorithmic}
\end{algorithm}

\paragraph{Joint upper bound.} The Joint method bypasses the loop entirely: the
classifier is expanded to the union label space upfront and a single training
pass runs over the concatenation of all sessions' data. It is the only method
that sees all data simultaneously and serves as the oracle reference of
Chapter~\ref{ch:experimental-setup}.

\paragraph{Convergence-based training.} The shared \texttt{train\_task} loop trains
each task to convergence rather than for a fixed number of epochs. A common
\texttt{EarlyStopper} (in \texttt{doccl/methods/base.py}) evaluates the task's
validation entity-F1 after each epoch, keeps a CPU snapshot of the best-scoring
weights, and stops once the score fails to improve for two consecutive epochs;
\texttt{restore\_best} reloads that snapshot before the task boundary. Because the
stopper lives in the base class, every method---regularisation, replay, distillation,
and the proposed remedy alike---inherits the identical stopping rule for free, which
is what makes the comparison fair under the protocol of
\S\ref{sec:exp-checkpointing}.

\paragraph{The proposed method (DocCL).} DocCL is implemented in
\texttt{doccl/methods/doccl.py} as a thin composition over existing infrastructure: it
reuses the EWC Fisher machinery for its depth-scaled penalty, the LwF-style frozen
teacher for output distillation, and the shared \texttt{ReservoirBuffer} for head
re-exposure replay, so it introduces no new training subsystem. The depth weights are
read from a \texttt{param\_groups\_by\_depth} grouping of the backbone and applied per
bucket ($\{\text{input}{:}0,\,\text{early}{:}0,\,\text{mid}{:}0.5,\,\text{late}{:}1.0,\,
\text{head}{:}2.0\}$ for the full method), and a \texttt{target\_depth} configuration
key selects the \emph{full}, \emph{head-only}, \emph{late-only}, or \emph{uniform}
variant that drives the component-targeting ablation of Chapter~\ref{ch:results}. The
method is registered under the same Hydra factory as the baselines, so it is selected
by name (\texttt{method=doccl}) on the identical harness.

\subsection{Per-Component Instrumentation}
\label{sec:impl-instrumentation}

The diagnostic of \S\ref{sec:method-diagnostic} is implemented as a set of hooks
that, at each task boundary, capture activations at the tracked layers (for CKA)
and accumulate squared gradients per parameter group (for Fisher), writing
per-run JSON dumps that are later aggregated into a long-format dataframe for
analysis and plotting. The instrumentation is decoupled from the methods so that
it can be attached to any run, including the naive-sequential pilot runs. Four
mechanisms make up the layer:

\begin{itemize}
  \item \textbf{Representational drift (CKA).} Forward hooks capture per-layer
  activations on a \emph{fixed} probe set---the same held-out documents are used at
  every task boundary so that representations are compared on identical inputs.
  Linear CKA between the activations of two checkpoints scores how much each layer's
  representation has changed; because it is invariant to orthogonal transforms and
  isotropic scaling, a drop signals genuine representational reorganisation rather
  than a trivial rotation. The probe activations are gathered through a hook helper
  and scored layer by layer.
  \item \textbf{Parameter importance (per-group Fisher).} Over a task's data the
  diagonal empirical Fisher accumulates squared gradients of the log-likelihood with
  respect to each parameter, summed within the eight named parameter groups
  (text word embeddings, 2D layout-position embeddings, image patch embedding,
  text attention, visual attention, cross-modal fusion, feed-forward, and
  classifier). Comparing the per-group Fisher before and after a task gives a
  per-component importance-drop profile that complements the CKA view.
  \item \textbf{Classifier-head expansion.} When a new task introduces new BIO
  labels, the classification head is grown to cover them while the rows
  corresponding to previously seen labels are preserved, so that old-label logits
  are not reset by the arrival of new classes. Formally,
  \begin{equation}
    \label{eq:head-expansion}
    W^{(t)} = \begin{bmatrix} W^{(t-1)} \\ W_{\mathrm{new}} \end{bmatrix},
    \qquad W_{\mathrm{new}} \sim \mathcal{N}(0,\,0.02^{2}),
    \qquad b_{\mathrm{new}} = 0,
  \end{equation}
  where the rows of $W^{(t-1)}$---the previously seen BIO labels---are copied
  unchanged so that old-label logits are exactly preserved, and
  $W^{(t)} \in \mathbb{R}^{|\mathcal{Y}_t| \times 768}$ for the label set
  $\mathcal{Y}_t$ after session $t$. Expansion is performed once by the
  training loop before each task, and the label$\leftrightarrow$index maps are
  updated in lockstep.
  \item \textbf{Modality ablation.} The pilot conditions are realised by zeroing
  input pathways \emph{in place} rather than by instantiating separate models: the
  text, visual, and layout streams are masked individually through a single forward
  argument, so C1--C4 share identical weights and differ only in which modalities
  reach the encoder. This is what makes the per-condition comparison
  apples-to-apples.
\end{itemize}

\paragraph{Code pointers.} For reproducibility, the components above map directly
onto the source: linear CKA and the activation hooks live in
\texttt{doccl/eval/cka.py}; the diagonal and per-group Fisher in
\texttt{doccl/eval/fisher.py}; classifier expansion, the eight-group
\texttt{param\_groups} mapping, and the \texttt{modality\_mask} forward argument in
\texttt{doccl/models/layoutlm\_wrapper.py}; and the method lifecycle hooks in
\texttt{doccl/methods/base.py}. The single Hydra entry point
\texttt{scripts/train.py} wires these together and resolves each method from its
registry.

\subsection{Datasets and Scenario Builders}
\label{sec:impl-datasets}

Dataset loaders expose FUNSD, CORD, and SROIE in the shared format, and scenario
builders assemble them into continual sequences (class-incremental, domain-incremental,
mixed) through a registry, so that a scenario is selected by name from the config.

\subsection{Compute and Deployment}
\label{sec:impl-compute}

\paragraph{Hardware tiers.} Experiments run on a single RTX 4090 (cloud), with a
local RTX 2060 reserved for debugging only; paper-result experiments are never
run on the debug machine. Determinism is enforced (fixed seeds, deterministic
cuDNN) so that CKA and Fisher patterns reflect signal rather than run-to-run
noise.

\paragraph{Memory management.} Two documented low-VRAM knobs allow the debug
tier to run the same code path: reducing the batch size from 8 to 2 and
enabling gradient checkpointing. Production runs use full fp32 precision---an
fp16 flag exists but is disabled by default---so no precision-related
nondeterminism enters the measurements.

\paragraph{Resource accounting.} Every run records wall-clock time per task,
parameter counts, and peak GPU memory in its \texttt{metrics.json}
(\S\ref{sec:impl-tracking}), enabling the computational-cost comparison of
Chapter~\ref{ch:results}.

\subsection{Experiment Tracking and Monitoring}
\label{sec:impl-tracking}

All runs report to Weights \& Biases under a single public project
(\url{https://wandb.ai/thanh-workspace/CL4IE}), with a structured tag
schema (\texttt{\{phase\}/\allowbreak\{scenario\}/\allowbreak\{method\}/\allowbreak seed\{seed\}}; pilot runs use
\texttt{pilot/\allowbreak\{condition\}/\allowbreak seed\{seed\}}), so that the full grid is queryable and
the result tables of Chapter~\ref{ch:results} can be regenerated from the tracked
logs. Each run is named \texttt{\{scenario\}\_\allowbreak\{method\}\_\allowbreak seed\{seed\}}, and its
per-run \texttt{results/\allowbreak<run>/\allowbreak metrics.json} holds the final \gls{aa}, \gls{bwt},
\gls{af}, and \gls{fwt}, the full performance matrix $R$, wall-time per task,
parameter counts, and peak GPU memory, with the raw matrix additionally saved as
\texttt{matrix.npy}. Downstream, \texttt{scripts/\allowbreak analyze\_results.py}
aggregates the runs into the LaTeX result tables and
\texttt{scripts/\allowbreak ingest\_to\_thesis.py}
copies them into the thesis source, so every reported number is regenerable from
logs. Table~\ref{tab:run-artifacts} lists the artefacts each run produces and

\section{Reproducibility}
\label{sec:impl-reproducibility}

\paragraph{Repository and environment.} The complete implementation is available
at \url{https://github.com/hoangthanh283/doccl} (branch \texttt{doccl}). The
environment is Python $\ge$3.10 with the minimum versions of
Table~\ref{tab:software-stack} pinned in \texttt{pyproject.toml}.

\paragraph{Seeds and determinism.} All main results use three seeds (42, 123,
7). cuDNN runs in deterministic mode with benchmarking disabled
(\texttt{torch.backends.\allowbreak cudnn.\allowbreak deterministic=True},
\texttt{benchmark=False}), and every run is fully specified by its Hydra
configuration.

\paragraph{One-command reproduction.} The diagnostic study---four conditions
$\times$ three seeds over FUNSD\,$\rightarrow$\,CORD\,$\rightarrow$\,SROIE---reproduces
with \texttt{bash scripts/run\_pilot.sh}; the main grid with
\texttt{bash scripts/run\_grid.sh}, where the \texttt{PHASE} variable selects
the core, advanced, selected-method, or ablation slices; and a single run via
the Hydra entry point of \S\ref{sec:impl-stack}. SROIE is prepared once by
\texttt{python scripts/prepare\_sroie.py} from a public HuggingFace mirror
(\texttt{mp-02/sroie}) or the ICDAR-2019 originals.

\paragraph{Tracked artefacts.} The public Weights \& Biases project of
\S\ref{sec:impl-tracking}, together with the per-run artefacts of
Table~\ref{tab:run-artifacts}, allows the result tables to be regenerated
end-to-end from logs.

\section{Summary}
\label{sec:impl-summary}

The framework pairs a small, component-separable backbone with a uniform
continual-method interface, a shared document pipeline, decoupled per-component
instrumentation, and structured experiment tracking, and it is reproducible
end-to-end through a public repository, a pinned environment, and result tables
regenerated directly from tracked logs. This design makes the diagnosis
attachable to any run and the baseline comparison strictly like-for-like, which
the next chapter relies upon.
